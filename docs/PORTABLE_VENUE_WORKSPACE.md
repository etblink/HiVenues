# Portable venue workspace

A portable venue workspace is an **offline, non-secret build artifact** that binds one accepted deployment-bound HV-5 authoring document to one explicit deployment target without embedding the target manifest into venue design/content authority.

The boundary is intentionally asymmetric:

- `venue-authoring.json` is the canonical **deployment-bound HV-5 authoring input**. Schema v1 contains deployment-owned `deploymentRef.id` plus the validated venue context/package; it is not the future deployment-agnostic venue-source artifact;
- `deployment-manifest.json` is the target-specific deployment input validated by the existing HV-2 deployment authority, and its resolved deployment ID must match `venue-authoring.json`;
- `runtime-bootstrap.json` is the canonical HV-4 bootstrap envelope produced from those two matching inputs and is directly consumable by ordinary isolated runtime admission;
- `bootstrap-review.json` is the normalized validated HV-4 composition for inspection;
- `workspace-manifest.json` is a derived inspection record that binds the other four files by UTF-8 byte length and SHA-256.

The current workspace manifest schema is **v2**. Its terminology intentionally distinguishes deployment-bound authoring from the planned deployment-agnostic venue source:

- `authority.deploymentBoundAuthoring` points to `venue-authoring.json`;
- the authoring file record role is `DEPLOYMENT_BOUND_HV5_AUTHORING_INPUT`;
- `inputDigestSha256` binds the canonical deployment-bound authoring bytes together with the canonical target deployment bytes used to derive this workspace;
- there is no `authority.venueSource`, `CANONICAL_PORTABLE_VENUE_SOURCE` role, or `sourceDigestSha256` field in schema v2.

Workspace-manifest schema v1 existed briefly in Git history after the first accepted workspace implementation and used those now-ambiguous names. That historical schema remains immutable provenance, but current tooling emits schema v2 and **must not interpret the v1 `venueSource` label as meaning deployment-agnostic source bytes**.

The workspace manifest is **not** a new configuration authority. Runtime admission still validates `runtime-bootstrap.json` through the accepted HV-4/HV-2/HV-1/HV-3 boundaries.

The accepted workspace is also **not** the deployment-agnostic venue-source layer. The selected next product lane defines that upstream source separately. Once accepted, the intended direction is:

```text
DEPLOYMENT_AGNOSTIC_VENUE_SOURCE
+ TARGET_SPECIFIC_DEPLOYMENT
-> DEPLOYMENT_BOUND_HV5_AUTHORING
-> PORTABLE_VENUE_WORKSPACE
```

HV-5 schema v1 remains accepted and unchanged; the new source layer is an upstream portability boundary, not a rewrite of the accepted authoring contract.

## Build one workspace

```text
node scripts/build-venue-workspace.js <authoring.json> <deployment-manifest.json> <output-directory>
```

The output directory must not already exist. The command claims that path with an exclusive directory creation before writing any file, so a concurrent creator wins cleanly rather than being replaced. If a file write fails after this process claims the directory, only that claimed incomplete directory is removed. The command validates both inputs, constructs the bootstrap, writes the five canonical files, and emits the exact `workspace-manifest.json` bytes to stdout. It performs no network request and does not start the application.

For identical validated input values that differ only in object insertion order, insertion order does not affect the generated bytes, input digest, workspace ID, bootstrap ID, or file hashes. Changing target-specific deployment facts while preserving the same deployment ID changes workspace identity without changing the HV-5 authoring bytes. Changing to a target with a different deployment ID currently requires a correspondingly rebound HV-5 authoring document; the selected deployment-agnostic venue-source layer is intended to make the upstream venue bytes independent of that later binding.

## Runtime boundary

`runtime-bootstrap.json` is the file intended for the existing explicit runtime-admission path. A later runtime operation can point `HIVE_VENUE_BOOTSTRAP_PATH` at that file; runtime admission then performs its own validation and deployment/runtime coherence checks before listening.

Building a workspace does **not** authorize or perform deployment, DNS changes, service installation, TLS configuration, Hive or Keychain writes, account onboarding, payments, moderation mutation, or any other external effect.

## What does not belong in a workspace

Do not place Hive private keys, passwords, API tokens, SSH keys, credentials, runtime databases, payment receipts, onboarding state, moderation state, environment secrets, or live production state in the HV-5 authoring input or deployment manifest. Existing non-secret document boundaries reject recognized secret/private material before a workspace can be built.

A deployment target may legitimately contain target-specific public facts such as runtime version, platform, public host, release root, storage paths, service name, and provenance filenames. Those facts remain deployment-owned and are expected to be regenerated or replaced when moving between hosting topologies. The workspace itself is therefore a target-bound build artifact and should be rebuilt for the selected destination.
