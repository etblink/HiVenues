# Portable venue workspace

A portable venue workspace is an **offline, non-secret build artifact** that binds one canonical venue authoring document to one explicit deployment target without turning deployment facts into venue design data.

The boundary is intentionally asymmetric:

- `venue-authoring.json` is the portable venue source validated by the existing HV-5 authoring authority;
- `deployment-manifest.json` is the target-specific deployment input validated by the existing HV-2 deployment authority;
- `runtime-bootstrap.json` is the canonical HV-4 bootstrap envelope produced from those two sources and is directly consumable by ordinary isolated runtime admission;
- `bootstrap-review.json` is the normalized validated HV-4 composition for inspection;
- `workspace-manifest.json` is a derived inspection record that binds the other four files by UTF-8 byte length and SHA-256.

The workspace manifest is **not** a new configuration authority. Runtime admission still validates `runtime-bootstrap.json` through the accepted HV-4/HV-2/HV-1/HV-3 boundaries.

## Build one workspace

```text
node scripts/build-venue-workspace.js <authoring.json> <deployment-manifest.json> <output-directory>
```

The output directory must not already exist. The command claims that path with an exclusive directory creation before writing any file, so a concurrent creator wins cleanly rather than being replaced. If a file write fails after this process claims the directory, only that claimed incomplete directory is removed. The command validates both sources, constructs the bootstrap, writes the five canonical files, and emits the exact `workspace-manifest.json` bytes to stdout. It performs no network request and does not start the application.

For identical validated source values that differ only in object insertion order, object insertion order does not affect the generated bytes, source digest, workspace ID, bootstrap ID, or file hashes. Changing the target deployment changes the workspace identity while preserving the venue source identity.

## Runtime boundary

`runtime-bootstrap.json` is the file intended for the existing explicit runtime-admission path. A later runtime operation can point `HIVE_VENUE_BOOTSTRAP_PATH` at that file; runtime admission then performs its own validation and deployment/runtime coherence checks before listening.

Building a workspace does **not** authorize or perform deployment, DNS changes, service installation, TLS configuration, Hive or Keychain writes, account onboarding, payments, moderation mutation, or any other external effect.

## What does not belong in a workspace

Do not place Hive private keys, passwords, API tokens, SSH keys, credentials, runtime databases, payment receipts, onboarding state, moderation state, environment secrets, or live production state in the venue authoring or deployment source documents. Existing non-secret document boundaries reject recognized secret/private material before a workspace can be built.

A deployment target may legitimately contain target-specific public facts such as runtime version, platform, public host, release root, storage paths, service name, and provenance filenames. Those facts remain deployment-owned and should be regenerated or replaced when moving the same venue between supported hosting topologies.
