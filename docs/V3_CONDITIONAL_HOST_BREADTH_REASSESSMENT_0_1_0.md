## 1. Purpose

S1-S4 have now proved the generalized v3 architecture through three materially different references:

- R1 migrated physical host;
- R2 native locationless creator/performer;
- R3 native release/premiere.

The accepted v3 family now includes provider-neutral source/migration/rendering, activity lifecycle/temporal/presence authoring, typed public actions, source-managed activity promo media, exact history/persistence, and complete browser-level Studio journeys through one orchestration family.

S5 asks one narrower question:

> **Which remaining host-specific capabilities still justify blocking the PM4 critical path before Studio product-language and interaction convergence begins?**

S5 is a routing/adjudication operation. It does not implement conditional breadth.

## 2. Governing product rule

Current doctrine distinguishes universal product obligations from conditional host traits.

A physical address, map, hours, menu, reservation provider, equipment inventory, gallery, ticket provider, merchant/payment role, and similar domain facts are conditional. Their absence from an unrelated host archetype is not a product defect.

Therefore:

```text
VALID_CONDITIONAL_FEATURE
!=
UNIVERSAL_PRODUCT_REQUIREMENT
!=
AUTOMATIC_CRITICAL_PATH_BLOCKER
```

Historical queue position and prior preregistration do not create current priority by inertia.

## 3. S5 classification vocabulary

For this reassessment each material residual family receives one current disposition:

```text
SATISFIED_OR_REEXPRESSED
    S1-S4 now satisfy the governing next-generation need, even if the old v2 wording differs.

CONDITIONAL_BACKLOG
    Legitimate host-specific capability retained visibly, but not required before S6.

CONVERGENCE_DEPENDENT

SEPARATELY_PRIVILEGED

V2_COMPATIBILITY_ONLY
    Preserve accepted legacy behavior; do not generalize it into the v3 product merely for symmetry.
```

Every family below also receives an explicit `BLOCKS_S6` adjudication.

## 5. Menu resource/section/item cardinality and ordering

### Finding

Menu authoring remains valuable for restaurant/bar/hospitality hosts. Accepted v2 menu scalar authoring is real prior evidence. The historically preregistered menu cardinality family, however, never became accepted implementation.

The host product contract explicitly classifies menus as conditional rather than universal.

### Adjudication

```text
DISPOSITION = CONDITIONAL_BACKLOG
BLOCKS_S6 = NO
BACKLOG = #224
```

### Reason

Implementing nested menu creation/removal/order now would deepen one physical archetype but would not materially reduce the next product risk: whether the v3 Studio feels like one coherent, high-quality product across host classes.

If a later restaurant-quality reference cannot reach its required generated-experience standard without menu cardinality, that evidence may promote the family from #224 under a separately frozen contract.

## 6. Program/equipment and other physical-host resource breadth

### Finding

Program/equipment scalar/lifecycle mechanics have substantial accepted v2 evidence. Additional cardinality or specialized physical-host controls may still be useful for workshop, venue, service or inventory-heavy archetypes.

They are not universal v3 obligations.

### Adjudication

```text
DISPOSITION = CONDITIONAL_BACKLOG
BLOCKS_S6 = NO
BACKLOG = #224
```

### Reason

S4 has already proved that cross-host orchestration does not require a separate transaction/save/application fork. Additional physical resource families should be added only when a supported reference proves their present product value.

## 7. Gallery, non-Hero media and broader managed-media admission

### Finding

S3 proves source-managed activity `PROMO` usage, while mature v2 evidence proves managed Hero media. A richer Gallery/non-Hero media vocabulary remains likely to matter for marketing-grade generated experiences.

The correct media surface is closely coupled to the desired generated composition and visual hierarchy.

### Adjudication

```text
DISPOSITION = CONVERGENCE_DEPENDENT
BLOCKS_S6 = NO
PRIMARY_DECISION_PRESSURE = S7_GENERATED_EXPERIENCE_VISUAL_CONVERGENCE
BACKLOG = #224
```

### Reason

Adding a speculative generalized media-control catalog before the target generated compositions are exercised would optimize control completeness rather than product quality. S7 should be allowed to demonstrate which semantic media usages are actually missing.

Provider upload remains outside this source-managed media decision.

## 8. Component catalog/cardinality and Private Events-style presentation

### Finding

Gallery/private-events-style components are legitimate for some hosts but not universal. Generic semantic component insertion/removal/reordering mechanisms already have accepted evidence.

### Adjudication

```text
DISPOSITION = CONVERGENCE_DEPENDENT
BLOCKS_S6 = NO
PRIMARY_DECISION_PRESSURE = S6_AND_S7
BACKLOG = #224
```

### Reason

S6 should first establish the operator-facing product language and interaction architecture for selecting/adding meaningful semantic content. S7 can then expose whether specific missing component kinds prevent a representative host from reaching the visual ceiling.

Do not bulk-complete a physical-archetype component catalog before that evidence exists.

## 9. Per-component recipe authority

### Finding

Bounded recipe selection remains consistent with HiVenues doctrine; arbitrary CSS/DOM authority remains forbidden. Existing global theme/recipe evidence is useful, but historical event-list-specific recipe work is superseded.

### Adjudication

```text
DISPOSITION = CONVERGENCE_DEPENDENT
BLOCKS_S6 = NO
PRIMARY_DECISION_PRESSURE = S6_STUDIO_PRODUCT_LANGUAGE + S7_VISUAL_NEED
BACKLOG = #224
```

### Reason

The primary unresolved question is not whether another dropdown can be added. It is how an ordinary operator should understand and manipulate design choices without seeing implementation-shaped controls. S6 should define that interaction language before broad recipe authority is expanded.

## 10. Reservation/ticket destinations versus provider execution

### Typed destination editing

S3 already supports provider-neutral visitor-facing action semantics such as `TICKETS`, `RSVP` and `RESERVE` with explicit HTTPS destinations and no provider inference.

```text
DESTINATION_AUTHORING = SATISFIED_OR_REEXPRESSED
BLOCKS_S6 = NO
```

### Reservation/ticket execution

Actually creating, modifying, purchasing or reconciling a reservation/ticket is a provider-side effect with provider-specific consequence semantics.

```text
PROVIDER_EXECUTION = SEPARATELY_PRIVILEGED
BLOCKS_S6 = NO
```

Such execution must not be smuggled into ordinary source authoring merely because the public CTA exists.

## 11. Payments, value and support operations

The host product contract explicitly separates ordinary authoring from Hive/value authority. A fully qualified HiVenue does not require payment transfer capability merely to prove Hive nativeness.

```text
DISPOSITION = SEPARATELY_PRIVILEGED
BLOCKS_S6 = NO
PAYMENT_OR_VALUE_AUTHORITY = NOT_GRANTED
BACKLOG = #224 / separately governed security operation when justified
```

A future translated `Support` experience must still distinguish vote/curation semantics from transfer/payment semantics at the consequence boundary.
