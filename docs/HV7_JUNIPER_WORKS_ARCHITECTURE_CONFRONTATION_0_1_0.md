## 5. Requirement-by-requirement adjudication

### JW-R001 — Independent venue identity

```text
DISPOSITION = FAIL__GENERAL_PLATFORM_REPAIR_REQUIRED
PRIMARY_FINDING = COMPATIBILITY_LEAKAGE_DEFECT
SECONDARY_FINDING = VENUE_PACKAGE_MODEL_GAP
```

**Supported today:** display name, logo, authored voice, venue imagery, venue copy, operator noun, and staff-role vocabulary already rebind through venue context/package. The Lantern Room proof demonstrates a meaningfully different venue using the shared renderer without Fourth Street-specific content.

**Failure:** independent public presentation identity is not complete. `views/common/header.ejs` visibly renders `Hive-Bar` for the shared shell, and `views/pages/onboarding/index.ejs` visibly uses `Hive-Bar` in customer-facing explanatory copy. Juniper would therefore inherit predecessor-product branding on public surfaces.

Separately, Juniper's required venue-owned visual theme is not represented in the current venue package.

The internal `hb-*`, `data-bar-logo`, or other compatibility names are not independently failures. The failure is candidate-facing leakage and missing venue-owned presentation authority.

## 7. Minimum repair capability envelope

This section is a **repair requirement envelope**, not implementation authorization and not a frozen code design.

### Repair capability A — Structured repeatable venue information

The venue-expression model must be able to represent Juniper's frozen program and advisory equipment-status collections without prose flattening.

Required properties include:

- stable item identity independent of array position;
- bounded collection cardinality;
- strict typed validation;
- the frozen item semantics and states;
- deterministic serialization;
- explicit intentional empty state;
- explicit unavailable state where the chosen data/provider design can fail;
- public rendering that does not infer physical closure or safety from unavailable web data.

The mechanism may be general, but it must not invent a mandatory venue-type taxonomy.

### Repair capability B — Safe HV-5 collection lifecycle authority

HV-5 must gain an explicit safe ordinary-operator mechanism for admitted repeatable collections.

It must support the frozen create/edit/state-change/remove/archive/order/group jobs as applicable while preserving:

- integration-owned identity;
- Hive binding protection;
- payment/security protection;
- deployment authority separation;
- derived-field protection;
- fail-closed unknown paths;
- atomic accepted-document semantics;
- deterministic canonical serialization.

Blanket ordinary-operator replacement of arbitrary parent containers is not acceptable.

### Repair capability C — HV-6 typed collection authoring

The native visual adapter must project the expanded HV-5 authority into meaningful controls for collection items and lifecycle actions.

It must preserve:

```text
HV5_OWNERSHIP_DERIVED_AUTHORITY
TRUTHFUL_REAL_RENDERER_PREVIEW
ATOMIC_APPLY_THROUGH_HV5
DISCARD_RESTORES_ACCEPTED_STATE
REJECTION_LEAVES_ACCEPTED_STATE_UNCHANGED
NO_RAW_JSON_REQUIREMENT_FOR_ORDINARY_STEWARD
NO_SHADOW_CANONICAL_MODEL
```

### Repair capability D — Venue-owned accessible theme

The venue package/authoring contract must admit a bounded visual-brand layer sufficient for an independently branded venue.

The mechanism should build on the existing generic venue tokens where useful and must preserve accessibility constraints. It must not grant arbitrary CSS, script, or DOM/component authority.

### Repair capability E — Public successor identity leakage removal

Shared candidate-facing output must stop identifying the product as `Hive-Bar` merely because of predecessor lineage.

The repair should use venue/site identity and/or the successor product identity where semantically appropriate while preserving legitimate internal Fourth Street production/provenance compatibility names.

## 9. Product interpretation

Juniper Works was a productive nominee precisely because it is not bizarre.

A workshop/tool-library naturally needs several kinds of information that change more often than static venue copy but do not belong in a full transactional line-of-business system. Programs and advisory equipment status expose a real product boundary between:

```text
STATIC_VENUE_EXPRESSION
and
ROUTINE_STRUCTURED_VENUE_OPERATIONS_INFORMATION
```

Hive-Venues currently handles the first well. HV-7 shows that a credible second venue nominee requires a safe bounded form of the second.

That is a valuable falsification result. It does not imply that Hive-Venues should become a generic CMS, arbitrary schema builder, booking suite, ERP, or IoT platform.

Likewise, the visual-brand finding is narrower than “make everything themeable.” A venue should be independently recognizable without allowing arbitrary CSS/script authority.
