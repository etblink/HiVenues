## 2. Why the historical matrix must be reconciled rather than replayed

The original PM1 reference contract froze four physical-host pressures:

```text
FOURTH_STREET_REAL_REFERENCE
JUNIPER_WORKS_SYNTHETIC_REFERENCE
RESTAURANT_PRIVATE_EVENTS_SYNTHETIC_ARCHETYPE
LIVE_MUSIC_SYNTHETIC_ARCHETYPE
```

That contract established durable product-quality obligations: venue/host brand dominance, meaningful design range, credible visitor information architecture, responsive quality, accessibility, honest capability states, performance/SEO readiness, and one semantic renderer/authoring system.

Subsequent product-doctrine reconciliation broadened HiVenues beyond physical venues. Current acceptance must include at least one first-class non-physical creator/performer host and must not treat physical-business facts as universal.

S1–S4 then proved one v3 source/parser/renderer/authoring family across:

```text
R1 = MIGRATED_PHYSICAL_HOST
R2 = NATIVE_LOCATIONLESS_CREATOR
R3 = NATIVE_RELEASE_PREMIERE
```

S5 separately adjudicated the remaining historical physical-host feature queue and canonically found:

```text
PRE_S6_CONDITIONAL_BREADTH_BLOCKER_COUNT = 0
```

Residual menu cardinality, deeper program/equipment breadth, Gallery/non-Hero media breadth, physical-only component catalog breadth, additional recipe controls, reservation/ticket execution, physical map/address enrichment, and payment/value execution remain legitimate conditional capabilities in #224. They do not become PM4 blockers merely because an older physical-host task matrix once named them.

Therefore S9 SHALL NOT:

- blindly replay six complete reference journeys;
- re-open S5 by treating every unimplemented historical physical feature as a release blocker;
- discard the PM1 quality pressures that those references were created to test;
- accept a narrower v3 product merely because its machine tests are green.

S9 instead reconciles **deep current release references** with **targeted historical pressure controls**.

## 4. Track A — Studio release review

Track A SHALL judge the current v3 HiVenues Studio, not the superseded v1/v2 editor as though it were the final product.

### 4.1 Deep operator journeys

R1/R2/R3 SHALL each complete a meaningful ordinary-host journey through the same Studio orchestration family.

Every deep journey must include, where semantically applicable:

1. open the accepted source into Studio;
2. identify/select the intended Activity without source knowledge;
3. edit ordinary visitor-facing content;
4. edit at least one semantically appropriate temporal/presence/access fact;
5. add or edit an appropriate public action;
6. add/reorder accepted source-managed promotional media where available;
7. preview through the real renderer;
8. Preview → Discard with exact accepted state preserved;
9. Preview → Apply;
10. Undo → Redo exact restoration;
11. explicit Save;
12. fresh-process reopen to the exact saved source;
13. inspect desktop/tablet/mobile presentation without independent content trees.

R1 must preserve physical/legacy provenance truth.

R2 must not fabricate address/merchant/physical attendance facts.

R3 must preserve RELEASE/NONE semantics without event/location fabrication.

### 4.2 Studio state coverage

Across the deep matrix, human and machine evidence together must cover:

- clean session/open state;
- selected semantic object;
- proposal/Preview state;
- Apply state;
- Discard state;
- Undo/Redo;
- unsaved draft;
- saved workspace;
- fresh reopen;
- validation failure;
- capability-disabled dependency state;
- keyboard completion of principal editing actions;
- responsive preview modes.

No ordinary journey may require JSON/source-code editing, source pointers, digest editing, raw command payloads, arbitrary CSS/HTML/JS, or provider-specific mutation controls.

### 4.3 Track A human questions

A reviewer must explicitly answer:

1. Can an ordinary host understand what they are editing without knowing the source schema?
2. Is the real generated consequence obvious before Apply?
3. Are Save, unsaved state, Preview, Apply/Discard, Undo/Redo, and recovery states trustworthy?
4. Does the Studio feel like a coherent 2026 product rather than a developer harness?
5. Can the same interaction model credibly serve R1/R2/R3 without host-specific application forks?

A machine-green journey is not sufficient for Track A acceptance.

## 5. Track B — generated experience release review

### 5.1 Deep visitor evidence

Each R1/R2/R3 deep reference SHALL be reviewed at:

```text
MOBILE = 390 x 844
TABLET = 834 x 1112
DESKTOP = 1440 x 1000
```

For each deep reference:

- Home at all three representative viewports;
- one Activity detail at mobile + desktop;
- navigation and primary action hierarchy;
- capability-enabled/disabled behavior appropriate to that reference;
- weak/empty/degraded presentation where the reference can express it without fabricating a provider result;
- no horizontal overflow;
- no image overflow;
- no technical/developer chrome in ordinary visitor language.

This yields a bounded deep visitor target of:

```text
HOME_SCREENSHOTS = 3 references x 3 viewports = 9
DETAIL_SCREENSHOTS = 3 references x 2 viewports = 6
DEEP_VISITOR_SCREENSHOT_TARGET = 15
```

Additional screenshots require an identified acceptance consumer; screenshot accumulation is not itself evidence quality.

### 5.2 Targeted historical pressure evidence

H1/H2/H3 SHALL be consumed as pressure controls, not automatically replayed as full S9 journeys.

Accepted prior artifacts may be reused only when:

1. their exact source/renderer/presentation bytes relevant to the assertion remain unchanged or the assertion is explicitly historical;
2. artifact provenance is recoverable;
3. S9 names the exact acceptance obligation the artifact satisfies;
4. no S9 product change has invalidated the evidence.

If any condition fails, recapture only the smallest viewport/page state needed for that pressure.

### 5.3 Marketing-grade rubric

Each deep current reference SHALL be scored independently on the PM1 dimensions:

1. host/venue brand dominance;
2. information architecture and visitor-goal clarity;
3. above-the-fold composition;
4. section rhythm and overall hierarchy;
5. typography and readability;
6. media treatment;
7. CTA/action clarity;
8. responsive composition;
9. accessibility and interaction quality;
10. content credibility / empty-state honesty;
11. platform attribution and optional-capability integration;
12. performance/SEO readiness.

Ratings remain:

```text
FAIL
NEEDS_WORK
STRONG
FLAGSHIP
```

Acceptance threshold:

- no deep reference dimension may be FAIL or NEEDS_WORK;
- brand dominance, composition/hierarchy, responsive quality, and product credibility must reach FLAGSHIP;
- every other dimension must be at least STRONG.

Human review must explicitly answer yes to the generalized PM1 questions:

> Would this experience be credible on the HiVenues marketing site?

> Could the represented independent host plausibly use this public experience without hiring a designer/developer to repair it?

For R2/R3, `host` replaces `venue` deliberately; physical-business language is not universal product authority.

## 7. Accessibility acceptance

Studio and generated experience remain separate accessibility surfaces.

### 7.1 Generated experience

Required review includes:

- WCAG 2.2 AA baseline;
- logical landmarks;
- coherent heading hierarchy;
- reading/focus order matching semantic content order;
- visible focus;
- meaningful accessible names;
- explicit alt/decorative media decisions;
- sufficient contrast;
- reduced-motion respect;
- no viewport-specific semantic-order divergence;
- 44px touch-target convention where practical;
- no inaccessible PDF-only content requirement.

### 7.2 Studio

Required review includes:

- complete keyboard operation for the accepted journey;
- non-drag alternatives for any drag-accelerated behavior;
- understandable selection/focus relationship between structure, Canvas, and inspector;
- programmatic announcement of validation/save outcomes;
- no focus trap in preview or editing state;
- distinguishable selected/focused states;
- mobile/tablet controls that remain operable and understandable.

Automated Axe evidence is necessary but insufficient.

## 9. Performance acceptance

S9 SHALL distinguish deterministic lab evidence from production field claims.

Production field goals remain the PM1 Core Web Vitals targets where field telemetry later exists:

```text
LCP <= 2.5 s
INP <= 200 ms
CLS <= 0.1
TARGET_PERCENTILE = 75th
SEGMENT = mobile / desktop
```

S9 does not claim production percentiles from synthetic runs.

S9.1 SHALL measure the accepted canonical product under one documented reproducible lab setup before numeric lab budgets are frozen.

At minimum record:

- transferred/static asset bytes by class;
- JavaScript bytes used by public generated experience versus Studio/application surface;
- image intrinsic/rendered dimensions and loading policy;
- layout stability;
- representative navigation/render timing;
- whether disabled capabilities avoid unnecessary capability/provider JavaScript or requests;
- number of external requests during the synthetic review harness;
- artifact size and review cost.

Numeric lab release budgets are an S9.1 result, not an S9.0 guess.

## 11. Finding taxonomy and remediation gate

Every S9 finding receives exactly one primary class before implementation begins:

```text
RELEASE_BLOCKER
IMPORTANT_NONBLOCKER
ECOSYSTEM_LEVERAGE_OPPORTUNITY
POLISH
NO_ACTION
```

### RELEASE_BLOCKER

A defect that prevents one or more binding PM4/S9 acceptance criteria from being satisfied.

Examples may include:

- commercially non-credible generated experience;
- unusable ordinary operator journey;
- material accessibility failure;
- source/renderer/Studio fork required for a supported host class;
- materially misleading or invented semantic/provider state;
- unacceptable measured performance under the later frozen lab budget;
- broken SEO/canonical semantics required by the release matrix.

Release blockers may enter bounded remediation after adjudication.

### IMPORTANT_NONBLOCKER

Meaningful product improvement that does not prevent PM4 acceptance.

It remains visible but does not automatically delay release.

### ECOSYSTEM_LEVERAGE_OPPORTUNITY

A measured user/product deficiency for which existing Hive/Hive-adjacent infrastructure may provide superior leverage compared with proprietary implementation or omission.

This classification does **not** authorize provider integration.

### POLISH

Visible quality improvement below the release-blocker threshold.

### NO_ACTION

Observation that is acceptable, intentional, already covered, or unsupported by evidence.

No code change is authorized merely because a reviewer proposed one.

For each deep reference, S9 SHALL explicitly ask:

### 12.1 Reference-specific pressure

R1 physical/live-music should ask whether optional payment/discovery/media integrations materially improve a real audience/host job.

R2 creator should explicitly pressure SPK/3Speak media, creator value/support interoperability, signer UX, and optional feed/syndication needs.

R3 release/premiere should pressure durable media, syndication/feed signaling, and creator support without turning a release into a false physical event.

H1 Fourth Street should preserve the historically real bounded Distriator participation/handoff precedent without treating Distriator eligibility/claims/payouts as HiVenues authority.

### 12.2 Advancement rule

A provider may enter implementation only when all are true:

1. a measured S9 finding identifies a concrete user/product deficiency;
2. the provider capability addresses that deficiency materially;
3. the provider can remain behind the accepted provider-neutral semantic boundary;
4. provider failure can degrade locally without corrupting host/Activity identity;
5. a separately governed implementation/security operation authorizes the work.

Provider novelty alone is insufficient.

Magi/Hive Engine stay deferred absent a concrete programmable/cross-chain/token requirement.

## 13. Astra / Cloud Browser credit-preservation protocol

Scarce Astra usage is reserved for independent product judgment.

```text
ASTRA_ROLE = INDEPENDENT_BROWSER_PRODUCT_REVIEW
ASTRA_REPOSITORY_MAINTENANCE = NO
ASTRA_CI_OPERATION = NO
ASTRA_LEGACY_CI_WAITING = NO
ASTRA_GIT_ARCHAEOLOGY = NO
ASTRA_BUILD_DEBUGGING = NO
ASTRA_INITIAL_CODE_MUTATION = NO
ASTRA_PRIMARY_REVIEW = ONE_BOUNDED_BLIND_PRODUCT_PASS
ASTRA_FOLLOWUP = TARGETED_RETEST_OF_ADJUDICATED_BLOCKERS_ONLY

PROJECT_LEAD_OWNS =
GIT
+ IMPLEMENTATION
+ CI
+ LEGACY_COMPATIBILITY
+ PROVENANCE
+ FINDING_ADJUDICATION
+ FINAL_ACCEPTANCE
```

### 13.1 Preconditions before spending Astra credits

Astra SHALL NOT be invoked until S9.1 has prepared:

- exact canonical build identity;
- direct browser entry points or one bounded launch path;
- a short review mission;
- required synthetic/test state;
- a bounded journey list;
- known machine-qualified invariants that Astra need not re-prove;
- explicit instruction not to run/watch GitHub Actions;
- explicit instruction not to inspect Git history unless the supplied product target is unusable.

The target must be usable without asking Astra to discover how to build or test HiVenues.

### 13.2 Blind-pass rule

The initial Astra pass should be as product-blind as practical.

Do not seed Astra with Project Lead presentation defects, visual annoyances, or preferred provider integrations merely to seek confirmation.

Disclose only facts required to:

- access the product;
- understand the intended host/user role;
- avoid unauthorized external effects;
- distinguish synthetic fixtures from real businesses.

Known Project Lead findings may be compared with Astra results after the independent pass.

### 13.3 Astra review lenses

One coordinated pass SHALL cover three perspectives.

#### Operator

Questions:

- Can I understand what I am editing?
- Can I predict the generated consequence?
- Do state/save/recovery interactions inspire confidence?
- Do I need web-development or Hive knowledge for ordinary work?

#### Audience / patron

Questions:

- Does this destination immediately feel credible and intentional?
- Can I understand the host and what is happening?
- Is the next useful action obvious?
- Does Hive capability help without dominating the experience?

#### Product adversary

Questions:

- What keeps this from flagship 2026 commercial credibility?
- Where does the product feel generic, unfinished, confusing, or technically shaped?
- Is meaningful Hive/Hive-adjacent leverage conspicuously absent?
- Is any ecosystem capability being imitated poorly rather than reused behind a narrow seam?

Astra SHALL NOT award quality credit for hidden engineering complexity that an ordinary user cannot experience.

### 13.4 Astra output taxonomy

Every Astra finding should include:

- reference/journey;
- viewport/state;
- concise observation;
- user consequence;
- evidence (browser-visible description and screenshot/reference where available);
- suggested primary classification from the frozen S9 taxonomy;
- confidence;
- whether ecosystem leverage may be relevant.

Astra does not decide final classification. Project Lead adjudication remains authoritative.

### 13.5 Follow-up use

After Project Lead remediation, Astra may receive a second bounded mission containing only accepted blockers that materially depended on human/browser judgment.

Astra SHALL NOT repeat the complete review by default.

```text
SECOND_FULL_ASTRA_AUDIT = NO_BY_DEFAULT
TARGETED_BLOCKER_RETEST = YES
```

## 15. Generalization failure tests retained for S9

S9 fails if any of the following is required for acceptance:

1. a host-class-specific source schema;
2. a host-class-specific renderer fork;
3. arbitrary raw HTML/CSS/script authority;
4. Fourth Street-specific strings/classes as generic platform truth;
5. creator/release references fabricated into physical venues;
6. Community required for public-only reference validity;
7. disabling Community leaves broken navigation or technical chrome;
8. an outbound ticket/reservation/support link implies transaction success/authority;
9. mobile requires a separately authored content tree;
10. weak secondary states are omitted to make screenshots look better;
11. Studio Preview diverges from the real renderer;
12. ordinary Studio output requires source-code repair;
13. provider-specific identity replaces host or Activity identity;
14. a provider outage corrupts unrelated host/Activity state;
15. PM4 can pass only by reopening S5-deferred conditional breadth without new evidence.
