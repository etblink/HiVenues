## 0. Why this document exists

The end-state product doctrine defines **what HiVenues is meant to become**.

This document defines **how a person should move through that product over time**.

The distinction is essential.

HiVenues could satisfy many high-level product goals while still delivering the wrong interaction model—for example:

- a technically powerful Studio that feels like an admin console;
- a beautiful wizard that traps users in fixed decisions;
- a “simple mode / advanced mode” split that creates two incompatible products;
- a template picker followed by hundreds of controls;
- an AI assistant that secretly generates arbitrary code rather than controlling the canonical host model;
- a first-run experience that front-loads Hive/provider complexity before the user has seen value.

This document prevents those forms of drift.

The governing interaction principle is:

> **Guided creation first, then progressively deeper creative control over the same canonical host.**

The user should never feel that they leave one product and enter another.

The first-run creator, Studio, responsive review, release flow, operations, history and future assistant-driven editing are different views and workflows over **one canonical host and one durable working state**.

---

# Part I — Journey doctrine

## 1. HiVenues starts as an art director, becomes a creative Studio, and remains an operating system for the host’s digital territory

The user journey has three broad eras:

### Create

HiVenues guides the operator from nothing to a convincing, truthful first draft with minimal jargon and without requiring design-system knowledge.

### Shape

The same draft opens into a progressively deeper Studio where the operator can refine content, media, composition, Voice, participation, responsive behavior and integrations at the level of control they actually want.

### Operate

After first Release, HiVenues becomes the ongoing workspace through which the host maintains Activities, Offers, media, public state, urgent updates, History, participation and future Hive/provider capabilities.

The product does **not** end at “Publish website.”

The mature relationship is long-lived.

---

## 2. Complexity should grow only when the user asks for more control

The amount of product complexity visible to the operator should increase in proportion to the amount of control they request.

A first-time bar owner should be able to create something excellent without understanding:

- composition-family internals;
- host graph structure;
- Mechanic ids;
- provider seams;
- release digests;
- CSS;
- Hive operations;
- technical provenance.

A sophisticated creator should be able to progressively access meaningful control over:

- composition;
- hierarchy;
- media;
- Voice;
- responsive treatment;
- participation semantics;
- Activities / Offers;
- provider bindings;
- Releases / History / restore;
- consequence review.

Both users operate the **same product and same canonical host**.

There is no separate “basic product” and “advanced product.”

---

## 3. Ask fewer questions; show more consequences

HiVenues should prefer **preview-driven decisions** over abstract configuration.

Rather than asking the user to understand concepts such as:

- hero treatment;
- density;
- information architecture;
- responsive stack policy;
- navigation model;
- typography scale;

HiVenues should show bounded, high-quality consequences using the user’s real host material whenever possible.

Examples:

Instead of:

> “Choose density: compact / standard / spacious.”

Show the resulting host composition and let the user choose which feels closer.

Instead of:

> “Choose hero type: split / full bleed / editorial.”

Show the real host three ways.

Instead of:

> “Configure navigation architecture.”

Let Direction establish a strong default and expose a bounded alternative only if the user wants deeper control.

This principle should make the product feel intelligent and visual without requiring opaque automation.

---

# Part II — Canonical journey stages

## 4. Stage 0 — Arrival / choose the host

The first screen should begin with the host, not with software configuration.

The product should ask questions equivalent to:

> **What are you making?**

and

> **What should people understand or do when they arrive?**

The user may identify as:

- venue;
- creator;
- artist;
- publication;
- community;
- organization;
- event/program;
- other host type.

This is guidance, not a rigid taxonomy lock.

The archetype should help HiVenues form useful initial assumptions while allowing the canonical host model to remain broader.

### The product should not begin with

- template selection;
- provider connection;
- Hive account connection;
- page-tree configuration;
- theme settings;
- DNS/deployment;
- billing complexity;
- blockchain concepts.

The first value proposition is the host’s world, not the platform machinery.

---

## 5. Stage 1 — Purpose

The first guided-creation moment establishes the host’s intent.

HiVenues should gather enough to understand:

- what this host is;
- what people should understand first;
- what action or relationship matters most;
- what tone/character should dominate;
- whether the host is primarily physical, online or hybrid.

The questions should be ordinary human questions, not design-system questions.

Examples:

- “What are you making?”
- “What should visitors understand right away?”
- “What would you most like people to do here?”
- “Does this happen in a place, online, or both?”

Different answers should meaningfully influence the generated first draft.

A bar may prioritize visiting.

A musician may prioritize listening or seeing shows.

A publication may prioritize reading/subscribing.

A community may prioritize joining/participating.

The user should not need to understand information architecture to establish these priorities.

---

## 6. Stage 2 — Presence & Material

The second guided-creation moment establishes **what is true and what material exists**.

HiVenues should gather only what the user reasonably has.

Possible material includes:

- display name;
- presence mode;
- location/address where applicable;
- presence/hours line where applicable;
- contact;
- short summary;
- story/purpose;
- real logo;
- real photography/artwork/media;
- social/external links where applicable;
- initial Activity if one actually exists;
- initial Offer if one actually exists.

### “I don’t know yet” is a valid answer

HiVenues must not force fabricated completeness.

The product should support:

- skip;
- add later;
- unknown;
- not applicable.

A bar should not be forced to invent events.

A creator should not need a physical address.

A new host should not need a complete brand/media kit.

A sparse truthful host should still be able to produce an intentional first draft.

### Material priority

Real media should be used immediately when supplied.

If real media is absent, HiVenues may use truthful abstract/procedural bootstrap art and strong typography.

It may never fabricate documentary facts.

---

## 7. Stage 3 — Direction

Direction is **guided art direction**, not template selection.

This should be one of the most distinctive HiVenues experiences.

The operator should see their emerging host rendered through multiple genuinely different composition directions using their actual material.

Early families may include concepts like:

- Poster;
- Editorial;
- Hospitality.

Future families may expand beyond these.

### Direction should answer a feeling question

The user should be able to react in ordinary language:

- “This feels bold and event-led.”
- “This feels editorial and reflective.”
- “This feels warm and welcoming.”
- “This one feels more like us.”

They should not need to understand:

- DOM structure;
- page recipes;
- spacing scales;
- component architecture.

### Direction is reversible

Choosing a direction must never feel irreversible.

The user should understand that they can revisit Direction later.

A later Direction change should:

- start from the current working version;
- preserve canonical content and durable object identity;
- identify affected presentation choices;
- protect manual edits through exact provenance/conflict rules;
- allow review before broad changes enter the working version;
- preserve unplaced content as recoverable.

Direction is not “rerun onboarding.”

---

## 8. Stage 4 — Participation

Participation is where HiVenues begins to expose its deeper platform advantage without forcing the user to learn Hive.

The product should ask what visitors should be able to **do**, not which blockchain mechanics should be enabled.

Examples:

- attend;
- RSVP;
- listen;
- watch;
- follow;
- join;
- respond;
- reserve;
- buy elsewhere;
- subscribe;
- support;
- recommend;
- add to calendar;
- receive updates.

### The operator chooses the social language

HiVenues may help the host decide:

- what an action should be called;
- how it should be visually represented;
- what tone/metaphor suits the host.

### The system owns consequence truth

Behind that language, HiVenues must preserve exact semantics.

The user should be able to inspect the truthful consequence when relevant, but should not need to configure low-level mechanics during first-run unless they deliberately ask for that depth.

### Accountless and unbound are valid

If the host has no Hive/provider binding yet, the product should:

- use local/accountless consequences where supported;
- use honest external links where appropriate;
- show unavailable/deferred capabilities honestly;
- never imply a Hive/provider effect occurred when it did not.

---

## 9. Stage 5 — First Draft Reveal

The guided journey should culminate in a meaningful reveal.

The product should mostly get out of the way and present the result.

The emotional message is:

> **Here is your place.**

The operator should see:

- their identity;
- real material;
- chosen Direction;
- meaningful responsive composition;
- truthful Activities / Offers where present;
- participation language;
- mobile/desktop confidence.

Nothing is live yet.

### Why this moment matters

The operator’s mental model should shift from:

> “I am configuring software.”

into:

> “I am shaping my place.”

That transition is central to HiVenues.

A first draft that looks obviously unfinished breaks the journey.

The reveal must be sufficiently complete that a user who wants little customization could make a few small edits and proceed toward Release.

---

## 10. Stage 6 — Seamless handoff into Studio

The first draft is already the Studio working version.

There is no:

- export/import;
- conversion step;
- second schema;
- “switch to advanced mode” migration;
- duplicated website definition.

Entering Studio simply reveals more control over the same host.

The user should retain the confidence and continuity established by the first-draft reveal.

The Studio should open with the actual rendered site as the primary workspace, not with an admin configuration screen.

---

# Part III — Progressive Studio control

## 11. Control layer 1 — Immediate editing

The most common edits should be immediately discoverable and low-friction.

Examples:

- edit text;
- replace image;
- adjust media focal point;
- update contact/presence facts;
- create/edit an Activity;
- create/edit an Offer;
- reorder permitted semantic sections;
- change a simple host-facing label;
- preview responsive output;
- Undo.

These tasks should generally not require opening a site-wide settings area first.

Direct selection in the canvas should be the primary route where appropriate.

---

## 12. Control layer 2 — Creative direction

When the user wants to shape the character of the site more deeply, they can enter creative lenses such as:

### Direction

Structural composition family and broad presentation strategy.

### Look

Bounded visual treatment such as:

- palette;
- type direction;
- density;
- emphasis;
- composition-aware media treatment;
- other validated parameters.

### Media

- roles;
- focal points;
- crop/position;
- replacement;
- alt/caption;
- galleries/sequencing where supported.

The product should show visual consequences rather than expose design tokens as abstract numbers wherever possible.

---

## 13. Control layer 3 — Semantic / Voice control

Voice should allow the operator to shape how participation and host concepts are expressed.

The interface should make a clear distinction between:

- visitor-facing term/presentation;
- underlying semantic consequence.

The operator may customize:

- labels;
- terminology;
- metaphors;
- explanatory copy;
- iconography/presentation where supported;
- host nouns/tone.

The product must prevent silent mechanic conflation.

A wording change should not unexpectedly turn RSVP into purchase, vote into tip, follow into community subscription, etc.

---

## 14. Control layer 4 — Operational control

The Studio must support long-lived operation, not just creation.

Operators should be able to understand and manage:

- working vs live state;
- Release review;
- Release History;
- restore-to-working-version;
- urgent live-first status changes;
- conflicts/stale state;
- Undo/recovery;
- Activity lifecycle;
- persistent media / participation state.

Operational controls should feel calm and trustworthy, not like repository/version-control tooling.

---

## 15. Control layer 5 — Integrations and consequential capabilities

Provider/Hive/integration controls should appear only when useful.

Potential areas may include:

- Hive identity/social/community binding;
- external ticketing/reservations;
- media providers;
- payments/value/support;
- discovery;
- notifications;
- feeds;
- other provider-neutral capabilities.

These controls should not dominate the default creative workflow.

They should make consequence and authority clear.

The product must never imply that changing a label or connecting a visual action automatically grants authority to execute an external effect.

---

# Part IV — Progressive disclosure, not modes

## 16. No Basic Mode / Advanced Mode split

HiVenues should avoid an explicit “basic” versus “advanced” product split.

That pattern tends to create:

- two mental models;
- duplicated settings;
- migration problems;
- inconsistent capabilities;
- a perception that the simple product is temporary and the real product is hidden elsewhere.

Instead, HiVenues should use **progressive disclosure**.

The default Studio feels simple because irrelevant controls are not visible.

Examples:

- select an image → image controls appear;
- select an Activity → Activity controls appear;
- open Voice → semantic translation controls appear;
- open Connect → provider-purpose controls appear;
- open History → historical/release controls appear;
- open Technical details deliberately → provenance/stable ids appear.

Power is contextual, not globally dumped into the interface.

---

## 17. The wizard is not a cage

Every meaningful guided-creation decision must remain revisitable.

The user should later be able to revisit:

- Purpose emphasis;
- Presence & Material;
- Direction;
- Participation;
- Look;
- Voice;
- provider bindings;
- Activities / Offers.

The guided creator generates a strong baseline.

It does not permanently own the host’s design.

The more the user learns what they want, the more Studio should let them refine it without requiring a restart.

---

# Part V — Returning user journey

## 18. Returning users go to the host workspace, not onboarding

Once a host exists, the normal entry point is the host’s Studio/home workspace.

The user should not repeat setup.

The returning workspace should make the important current state legible at a glance:

- host identity;
- live state;
- unpublished work;
- important current/upcoming Activities;
- relevant operational alerts;
- easy path back to the canvas;
- Preview / Release state.

The product should prioritize **what needs attention now** rather than replaying first-run explanations.

---

## 19. Routine operation should be faster than initial creation

Common returning actions should become very direct:

- update an Activity;
- cancel an Activity urgently;
- replace a photo;
- adjust contact/presence information;
- add an Offer;
- publish a small set of changes;
- review history;
- restore earlier work;
- add a new capability.

The operator should not be forced back through broad site setup just to make a narrow maintenance change.

---

# Part VI — Release journey

## 20. Review before public consequence

The user should be able to create freely without publication anxiety.

When ready to publish, HiVenues should provide an ordinary-language Release review that answers:

- what is changing;
- what remains unchanged;
- whether anything is still unpublished;
- whether any external consequences are separate and not included.

The final action should be explicit.

Release should not feel like a generic “Save” button.

It is the boundary between working state and public website state.

---

## 21. Release success should return the user to operation, not dead-end celebration

After Release, the operator should see confirmation of:

- what became live;
- current Release identity/time in human terms;
- useful next actions;
- whether unpublished work still exists.

The product should not suggest that the host is “finished forever.”

The mental model is ongoing operation.

---

## 22. Urgent operations are a distinct journey

A cancellation/status emergency should not force the operator to publish unrelated drafts.

The urgent journey should:

1. begin from the live public state;
2. identify the narrow urgent change;
3. show what will change now;
4. show what remains live;
5. show what unrelated work remains unpublished;
6. publish only the dependency-closed urgent consequence;
7. return the operator to their preserved working state afterward.

This journey should remain visually and semantically different from an ordinary full Release.

---

# Part VII — Error and recovery journey

## 23. Errors should preserve momentum

An error should answer:

1. what happened;
2. what the operator can do next;
3. what state was preserved.

The product should preserve valid submitted material whenever possible.

It should not clear unrelated fields because one value failed validation.

It should not expose:

- stack traces;
- filesystem paths;
- raw internal ids as primary explanation;
- module names;
- repository terminology.

Errors are part of the product experience, not debugging output.

---

## 24. Conflict recovery should be comprehensible to nondevelopers

If an edit is stale, the product should fail closed and explain the situation in ordinary language.

The user should be able to understand:

- newer work exists;
- their attempted change was not silently applied;
- what recovery path is available.

The product should not require knowledge of revision numbers/digests to resolve common conflicts.

Technical detail may be available secondarily.

---

# Part VIII — Mobile journey

## 25. Mobile is not a compressed desktop Studio

At narrow widths, HiVenues should prioritize one task/workspace at a time.

A mature mobile Studio should use patterns such as:

- compact top-level host/status bar;
- intentional Page / Activities / Site navigation;
- canvas-first normal state;
- contextual bottom sheet for quick edits;
- full-screen editor for long text / Activity creation / media / release review;
- explicit Preview mode;
- clear back/close behavior;
- touch-sized actions;
- no required hover;
- no precision-dependent drag;
- no permanent two-column inspector layout.

The user should still feel that they are shaping the same host, not using a stripped-down administrative companion app.

---

## 26. Responsive review is part of ordinary creation

The operator should be able to understand desktop and mobile visitor consequence without maintaining separate content trees.

HiVenues should make mobile output easy to inspect throughout creation, not only at the end.

Where responsive-specific controls exist, they should be bounded and explicit.

A user should not need to become a responsive web designer to achieve a good result.

---

# Part IX — Future assistant / AI journey

## 27. Conversational assistance can be another controller for the Studio

A mature HiVenues may support natural-language requests such as:

- “Make this feel warmer.”
- “Put more emphasis on our live shows.”
- “This photo matters more.”
- “Make mobile less dense.”
- “Make us feel more like a neighborhood institution and less like a nightlife brand.”
- “I want people to notice the membership first.”

The assistant should translate these requests into **bounded semantic/presentation proposals over the canonical host model**.

It must not become an independent authoring engine that secretly generates arbitrary HTML/CSS/JS outside Studio’s model.

### Assistant principle

> **Conversation is another controller for the Studio, not another source of truth.**

Assistant changes should:

- target canonical objects;
- respect composition contracts;
- preserve accessibility/responsive constraints;
- preserve consequence truth;
- remain reviewable/reversible;
- participate in normal draft/history/conflict semantics.

---

# Part X — First-run success criteria

## 28. The first-run user should reach value before complexity

A successful first-run session should allow a capable nondeveloper to reach a credible first draft without needing to understand:

- Hive;
- provider configuration;
- website architecture;
- responsive CSS;
- page-tree mechanics;
- deployment;
- source code.

The user should encounter deeper complexity only when it becomes relevant to something they want to accomplish.

---

## 29. First-draft quality is a product requirement

Guided creation is not successful merely because it produces a valid host graph.

The first draft should be visually credible enough to create trust.

The first-draft reveal should already demonstrate:

- host identity;
- meaningful Direction;
- responsive competence;
- truthful sparse-state handling;
- real media integration where supplied;
- a clear visitor hierarchy;
- no obvious placeholder/admin language.

A user should not have to redesign the site from scratch after onboarding.

---

# Part XI — Anti-patterns

## 30. Journey anti-goals

### Do not begin with templates

Direction should emerge from the host and its material, not force the host into a generic catalog before HiVenues understands it.

### Do not begin with Hive connection

The user should understand product value before infrastructure binding.

### Do not front-load every decision

Ask enough to render; then let the user react to the result.

### Do not require complete facts

Unknown and add-later states are normal.

### Do not create separate wizard and Studio schemas

The guided draft is the Studio working version.

### Do not trap users in wizard choices

Direction, Voice, Look, participation and material must remain revisitable.

### Do not create Basic / Advanced products

Use progressive disclosure.

### Do not turn Studio into settings navigation

The canvas and semantic object should remain primary.

### Do not hide consequence truth behind branded language

Voice changes presentation, not mechanics.

### Do not let AI bypass the canonical model

Assistant requests must become bounded, reviewable Studio changes.

### Do not treat publication as the end of the journey

HiVenues is an ongoing operating workspace.

---

# Part XII — Journey qualification

## 31. The end-to-end journey test

A strong HiVenues candidate should allow an independent nondeveloper to complete this sequence without implementation coaching:

1. arrive with a real or synthetic truthful host;
2. explain purpose in ordinary language;
3. provide available presence/material;
4. skip unknown/not-applicable facts without penalty;
5. compare multiple real Directions using their content;
6. choose visitor participation in host-native language;
7. receive a credible first-draft reveal;
8. enter Studio without conversion/import;
9. make direct canvas edits;
10. create/edit Activity or Offer as relevant;
11. replace/edit media;
12. revisit Direction/Look/Voice without losing canonical content;
13. inspect desktop/mobile output;
14. understand working/live state;
15. review and make an explicit Release;
16. return later and make routine maintenance edits quickly;
17. handle an error/conflict without developer intervention;
18. use History/restore safely;
19. perform an urgent live-first change without publishing unrelated work;
20. optionally add deeper integrations/capabilities only when desired.

If the user needs source code, raw JSON, CLI work, Project Lead coaching or hidden implementation knowledge to complete a normal step, the journey is incomplete.

---

## 32. The emotional journey test

The product should produce these successive mental states:

### Arrival

> “This is about my place/project, not about learning a platform.”

### Guided creation

> “It understands what I’m trying to make.”

### Direction

> “I can see what different creative directions would actually mean for me.”

### First draft reveal

> “This already feels like something I could own.”

### Studio

> “I can shape this directly, and deeper controls are there when I need them.”

### Release

> “I understand what is about to become public.”

### Ongoing operation

> “This is where I run my digital presence.”

If the dominant mental states instead become:

- “Which template do I pick?”
- “Where is that setting?”
- “Why do I need to know what Hive does?”
- “Am I in the editor or preview?”
- “What will this button publish?”
- “I need a developer to fix this,”

then the journey has drifted.

# Part XIII — Governance

## 33. Journey precedence

This document is the canonical interaction doctrine beneath the end-state product doctrine.

Future work should distinguish:

- **product doctrine** — what HiVenues is;
- **journey doctrine** — how operators should move through it;
- **current scope** — what a bounded phase implements;
- **current UI** — what the present interface happens to do;
- **qualification** — what evidence proves about that UI.

Current UI behavior does not become canonical journey merely because it exists.

A phase may implement only part of this journey, but must label that limitation honestly.

---

## 34. Mandatory journey check for major UX work

Before accepting a major Studio/onboarding/flow change, Project Lead should ask:

1. Does the journey begin with the host rather than software configuration?
2. Are we asking human intent questions rather than technical/design-system questions?
3. Are unknown/add-later states first-class?
4. Does the user see real consequences earlier than abstract settings?
5. Is Direction shown with the host’s real material?
6. Does the first draft look credible before Studio handoff?
7. Is the first draft already the Studio working version?
8. Is the canvas primary?
9. Is deeper control progressively disclosed rather than mode-split?
10. Can guided choices be revisited safely?
11. Does mobile have an intentional task model rather than a compressed desktop shell?
12. Is consequence truth preserved under Voice/metaphor?
13. Does returning use prioritize current operation rather than onboarding repetition?
14. Are release/conflict/urgent flows understandable to a nondeveloper?
15. Could a future assistant operate through the same canonical model rather than bypass it?

A major UX change that fails these questions requires explicit justification or rejection.

---

## 35. Amendment rule

This journey may evolve as real operator evidence accumulates.

But changes must be deliberate and versioned.

A journey revision should state:

- what changed;
- why;
- what evidence supports the change;
- which product-doctrine or implementation contracts are affected.

No temporary UI, beta workaround, implementation limitation or customer-specific accommodation may silently amend this journey.

---

# Final journey formulation

> **HiVenues begins by helping a person articulate the host they are trying to create, uses truthful material to art-direct a strong first draft, reveals that draft as a place they can already recognize as their own, then progressively exposes deeper creative, semantic, operational and integration control over the same canonical host—without forcing them to learn web development, blockchain mechanics or product internals.**

The shortest formulation is:

> **Guided creation first. Progressive control afterward. One host throughout.**
