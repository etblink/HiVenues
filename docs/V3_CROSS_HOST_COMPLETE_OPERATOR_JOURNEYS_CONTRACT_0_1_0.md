# HiVenues V3 Cross-Host Complete Operator Journeys Contract 0.1.0

Status: **FROZEN IMPLEMENTATION CONTRACT**

## 1. Purpose

S1 proved one provider-neutral v3 source/migration/renderer family across a migrated physical host, a native locationless creator, and a native release/premiere.

S2 proved one strict reversible stale-safe activity authoring and local persistence family across those references.

S3 proved typed visitor-facing public actions and source-managed promotional-media usage through the same v3 transaction family.

S4 is the first composition milestone. It asks:

> Can an ordinary operator complete a meaningful HiVenues activity job from start to finish across R1/R2/R3 using one coherent Studio workflow, while the typed v3 source remains authoritative and the real renderer shows the public consequence?

S4 SHALL compose accepted S1-S3 authority. It SHALL NOT become another schema-breadth operation.

## 2. Entry discipline

The implementation SHALL begin from the exact canonical S3 merge named above.

A missing primitive discovered by a complete journey SHALL NOT be silently added. If an accepted S1-S3 command cannot express a required ordinary journey step, that condition must be isolated and reported as a separately classified gap rather than smuggled into S4.

S4 may add only the minimum orchestration and Studio presentation needed to expose already-accepted v3 operations coherently to an operator.

## 3. Shared Studio orchestration boundary

S4 SHALL provide one v3 Studio orchestration surface that:

- opens one accepted v3 source into one S2/S3 authoring session;
- selects an activity by stable activity identity;
- exposes ordinary S2 text/lifecycle/access/temporal/presence controls appropriate to that activity;
- exposes S3 public-action and managed-media controls;
- previews each proposed change through the real v3 renderer before acceptance;
- supports Apply and Discard;
- supports exact Undo and Redo;
- supports explicit local Save and fresh reopen when a workspace is configured;
- never exposes raw source JSON, source pointers, history payloads, digest editing, or provider-specific mutation controls as ordinary operator authority.

The surface may display diagnostic digests for qualification evidence, but an operator SHALL NOT edit or supply them.

The same session, proposal, history, persistence, and rendering families SHALL serve every S4 reference. Host-specific transaction engines, save paths, renderer forks, or generic page-builder escape hatches are forbidden.

## 4. R1 — migrated physical host journey

Using the migrated physical reference, one complete browser-level journey SHALL prove that an operator can:

1. select an existing activity;
2. edit ordinary visitor-facing text;
3. preserve or deliberately edit occurrence/physical-presence facts through accepted S2 controls;
4. preserve migrated `LEGACY_EXTERNAL` action provenance;
5. add a native `TICKETS` or `RSVP` action;
6. edit/reorder public actions without semantic inference;
7. add/reorder existing source-managed `PROMO` media while compatibility media remains provenance;
8. preview real generated activity output;
9. Apply, Undo, and Redo with exact digest/source consequences;
10. Save and fresh-reopen exactly when persistence is enabled.

No physical/provider fact may be guessed from URL, label, or provider identity.

## 5. R2 — native locationless creator journey

Using the native creator reference, one complete browser-level journey SHALL prove that an operator can:

1. select the activity without a physical-host fork;
2. edit ordinary visitor-facing text;
3. preserve or edit accepted online presence through S2 controls;
4. add native `WATCH` and/or `INFO` actions;
5. add/reorder source-managed `PROMO` media;
6. preview real generated activity output;
7. Apply, Undo, and Redo exactly;
8. Save and fresh-reopen exactly when persistence is enabled.

The journey SHALL NOT fabricate physical venue/address facts.

## 6. R3 — native release/premiere journey

Using the native release reference, one complete browser-level journey SHALL prove that an operator can:

1. select the release activity through the same Studio orchestration;
2. edit ordinary visitor-facing text;
3. preserve genuine `RELEASE` temporal semantics;
4. preserve `NONE` presence where appropriate rather than inventing event/location facts;
5. add native `LISTEN`, `WATCH`, `INFO`, and/or `CALENDAR` outbound actions as appropriate;
6. add source-managed `PROMO` media;
7. preview real generated activity output;
8. Apply, Undo, and Redo exactly;
9. Save and fresh-reopen exactly when persistence is enabled.

`CALENDAR` remains outbound HTTPS navigation only. S4 does not schedule, publish, purchase, reserve, or mutate an external service.

## 7. Real browser evidence

S4 qualification SHALL exercise the operator surface with pinned Chromium using the repository's existing browser-evidence conventions.

For each R1/R2/R3 journey, evidence SHALL include:

- a real Studio page, not a direct command-constructor-only test;
- a real v3 renderer preview;
- keyboard-operable completion of the principal editing action;
- Preview -> Discard proof;
- Preview -> Apply proof;
- Undo -> Redo proof;
- visible public-renderer consequence;
- no horizontal overflow at the tested viewport;
- no serious or critical WCAG 2 A/AA axe findings in Studio or preview;
- bounded screenshots and a machine-readable evidence manifest;
- zero external-effect diagnostics.

S4 is not S6/S7 visual convergence. Browser evidence judges journey completeness, semantic coherence, accessibility, and truthful renderer consequence—not final visual polish.

## 8. Cross-host divergence audit

Before qualification, the implementation SHALL record whether R1/R2/R3 required any host-specific branching.

Legitimate semantic differences include the values/types already represented by v3, such as physical versus online versus no presence, and occurrence versus release temporal forms.

The following are S4 failures unless separately justified by an existing accepted contract:

- separate transaction engines by host class;
- separate save/reopen paths by host class;
- separate Studio applications by host class;
- provider-name/URL inference;
- raw-source editing to finish a journey;
- arbitrary `if hostType` behavior that duplicates an accepted semantic discriminator already present in v3.

## 9. Explicit non-scope

S4 does not authorize:

- new v3 schema breadth merely for convenience;
- S5 conditional host-breadth work;
- S6 Studio product-language/interaction convergence;
- S7 generated-experience visual convergence;
- generic component/page/cardinality authoring;
- arbitrary CSS/DOM/page-builder authority;
- media file ingestion/upload;
- provider upload or provider mutation;
- Hive broadcast/signing or Keychain/wallet signing;
- Hive social-root mutation;
- Podping/feed publication;
- ticket or reservation execution;
- checkout, payment, transfer, donation, vote, or value operations;
- production deployment/routing;
- Fourth Street production mutation.

## 11. Qualification requirements

S4 is qualified only if executable evidence proves all of the following:

1. one Studio application/orchestration family serves R1/R2/R3;
2. one S2/S3 transaction/session/history family serves R1/R2/R3 unchanged;
3. one v3 renderer family is the preview authority for all three references;
4. no v2 source/parser/renderer behavior is modified to fake v3 completion;
5. each reference completes its required ordinary journey through browser controls;
6. ordinary operators are not required to edit raw JSON, source pointers, command payloads, or digests;
7. Preview leaves accepted draft and persistent state unchanged;
8. Discard returns to the exact accepted source/digest;
9. Apply adds the accepted change through the existing transaction engine;
10. Undo/Redo are canonical-source/digest exact;
11. local Save + fresh reopen is exact where persistence is enabled;
12. public action identity/role semantics and managed-media composite identity remain S3-exact;
13. activity identity and slug remain stable unless an already-accepted S2 command explicitly governs otherwise;
14. R1 preserves migrated provenance while admitting native action/media operations;
15. R2 completes without fabricated physical facts;
16. R3 preserves RELEASE/NONE semantics without event/location fabrication;
17. browser evidence shows real renderer consequences for each reference;
18. each reference has no serious/critical accessibility findings and no horizontal overflow in the tested viewport;
19. cross-host divergence audit finds no host-specific transaction/save/application fork;
20. zero external effects occur;
21. full pre-existing deterministic suite remains green on Ubuntu and Windows;
22. production dependency audits remain green on Ubuntu and Windows;
23. S4-specific browser evidence runs in CI on the exact qualified candidate.
