## 0. Revision model

This document inherits the 0.1.0 Canonical User Journey in full except where strengthened below.

The governing interaction shorthand remains:

> **Guided creation first. Progressive control afterward. One host throughout.**

0.2.0 makes explicit that the journey grows beyond shaping a single landing page into operating a complete host-specific frontend territory.

---

# Part I — Journey eras

## 1. The mature journey is Create → Shape → Participate → Review → Release → Operate

These are interaction eras, not mandatory navigation labels.

### Create

Get from truthful host material to a convincing first draft without design-system or Hive expertise.

### Shape

Refine the host’s visual world, page/route structure, content, media and composition through progressive control.

### Participate

Define what visitors can do and how those mechanics are expressed in host-native language and visual form.

### Review

Inspect the complete working experience across routes, responsive states and consequences before publication.

### Release

Create an explicit reviewed public version without accidentally executing unrelated external effects.

### Operate

Maintain Activities, Offers, content, community, media, participation, integrations, urgent changes, History and future host-native Hive/value capabilities over time.

The product does not end at the home page or at first Release.

---

# Part II — First-run remains guided but must point toward the full territory

## 2. Guided creation should seed an information architecture, not lock one in

The initial journey remains:

> **Purpose → Presence & Material → Direction → Participation → First Draft Reveal**

The resulting first draft may be intentionally simple.

However, HiVenues should already make a strong semantic decision about the host’s likely structure:

- primarily one-page;
- Activity-led;
- publication/feed-led;
- creator/media-led;
- hospitality/offer-led;
- community-led;
- another host-appropriate structure.

The operator should not configure a technical sitemap during first-run.

The initial structure is a high-quality proposal that can deepen later without replacing the canonical host model.

---

## 3. Direction comparison should show real consequences using the same host

Direction selection must use the host’s actual truthful material wherever possible.

As the product matures, Direction comparison should be capable of showing differences in more than hero/section arrangement, including where appropriate:

- navigation;
- route/page grouping;
- Activity discovery;
- feed/editorial structure;
- Offers/menu/catalog treatment;
- media choreography;
- community/profile surfaces;
- host-native participation placement;
- desktop/mobile behavior.

The operator should be choosing among coherent host worlds, not themes.

---

# Part III — Studio deepens into territory authoring

## 4. Immediate editing remains contextual

Common edits should still begin from the rendered experience or an obvious semantic object.

Examples now include:

- text and media;
- Activity/Offer;
- feed/post content where supported;
- profile/community presentation where supported;
- navigation label/structure within bounded semantic rules;
- host-native action language;
- galleries and media roles;
- route/page emphasis;
- responsive treatment.

The operator should not have to locate the database-like settings page that owns an object before editing it.

---

## 5. Structural control is semantic, not arbitrary page building

When operators want deeper control, Studio should allow them to shape the host territory through meaningful decisions such as:

- choose/revise Direction;
- choose among admitted compositions/recipes;
- change bounded navigation models;
- emphasize or de-emphasize semantic regions;
- reorder/group compatible sections;
- change gallery/list/timeline treatments;
- change typography/spacing/density within validated systems;
- choose route/page treatment where the host supports multiple surfaces;
- decide how participation/community mechanics appear.

The user is shaping a semantic frontend, not editing arbitrary DOM.

---

## 6. Participation control should become visually host-native

The operator should be able to understand three layers without conflating them:

1. **Mechanic** — what really happens.
2. **Voice** — what the host calls it.
3. **Presentation** — how it appears in this Direction/composition.

For example, a vote/recommendation mechanic may be represented through different labels, SVG iconography, metaphors and placement in different host worlds while preserving the same exact mechanic and consequence disclosure.

The user should never need to learn blockchain terminology merely to create an expressive host-native action.

---

# Part IV — Review means the complete working experience

## 7. Review must cross route and consequence boundaries

A mature Review experience should let the operator verify the **working version** as a coherent frontend territory, not merely inspect a home-page screenshot.

Depending on the host, Review should include paths through:

- Home;
- Activities and Activity detail;
- Offers/menu/catalog;
- Feed/community;
- post/discussion detail;
- gallery/media;
- profiles/people;
- Visit/About/Contact;
- host-native account/resource/value surfaces when admitted.

Internal navigation must remain in the working-preview context.

No link may silently escape into the live Release merely because the public route already exists.

---

## 8. Responsive Review is not device cosplay

Built-in width review should clearly be presented as a **representation of available composition space**, useful for judging component behavior.

Native viewport/device qualification remains separately necessary.

Operators should be able to understand:

- wide composition;
- narrow composition;
- actual mobile Studio behavior;
- actual mobile public behavior;
- relevant bounded responsive options such as focal point, stacking, density or emphasis.

The product should not claim that a decorative embedded frame perfectly emulates physical devices.

---

# Part V — Mobile Studio

## 9. Mobile authoring must prioritize tasks, not compress desktop architecture

The 0.1.0 one-workspace-at-a-time principle remains controlling.

As Studio grows, mobile must not become a stack of every desktop panel.

Use interaction patterns such as:

- compact host/workspace switcher;
- canvas-first normal state;
- contextual bottom sheets for quick edits;
- dedicated full-screen editors for Activities, long-form content, media, composition and Release review;
- clear back/context behavior;
- touch-sized SVG icon controls with accessible names;
- explicit working/live/release state.

A feature is not mobile-complete because it technically fits in 390 CSS pixels.

---

# Part VI — Returning operation

## 10. Returning users should see what changed and what needs attention

The returning workspace should prioritize host operation, including as applicable:

- live versus working state;
- unpublished edits;
- current/upcoming Activities;
- feed/content state;
- community or participation attention;
- media/integration failures;
- provider degraded states;
- pending consequences;
- quick path to the canvas;
- Release/History/urgent state.

Do not replay onboarding merely because more end-state capabilities exist.

---

## 11. External consequences remain deliberate sub-journeys

A Hive/social/payment/provider action may be visually integrated into the host experience, but its execution remains a separate consequence journey when authority is required.

The operator or visitor should see, at the point of consequence:

- what will happen;
- which identity/account acts;
- whether the result is public;
- whether value moves;
- which authority is required;
- whether the provider is available;
- whether the result is pending or canonically confirmed.

This truth should not contaminate ordinary creative editing with provider jargon before it is relevant.

---

# Part VII — Synthetic-first end-state qualification

## 12. The product must be internally mature before independent Astra use

Independent Astra testing is for finding non-obvious product/operator failures, not for rediscovering unfinished visual design already visible in screenshots.

Before opening a synthetic Astra campaign, Project Lead must have internally exercised a substantially complete product.

---

## 13. Feature-saturated reference host journey

The first end-state qualification specimen should be a clearly fictional maximal host containing every mutually compatible capability we intend Astra to test.

It should be created through normal Studio operation and should include rich enough truth to exercise, where applicable:

- multiple Activities and lifecycle states;
- Offers;
- rich media/logo/gallery;
- story/about/visit/contact;
- community/feed/posts/discussion;
- profile/member/patron surfaces;
- Voice and host-native participation;
- Hive read/write mechanics under the current authority ceiling;
- Release/History/Restore/urgent/conflict behavior;
- desktop and mobile states.

No fixture/source intervention should substitute for ordinary operator authoring when the feature is supposed to be Studio-authored.

---

## 14. Same-host Direction/composition journey

Astra should then take that exact semantic host through multiple Directions and multiple admitted compositions/recipes.

The purpose is to compare like-for-like output.

The operator should judge whether each result feels like a plausible professional frontend for the same host with a genuinely different art direction—not merely different colors, typography or section order.

Canonical content and domain identity must survive the changes.

---

## 15. Synthetic archetype suite before Fourth Street

After the maximal specimen, Astra should create several additional fictional hosts with deliberately different needs and information architectures.

The exact suite may evolve, but should stress categories such as:

- nightlife/hospitality;
- artist/musician/creator;
- publication/editorial;
- community/organization;
- conference/gallery/hybrid local business.

These are not visual demos. They are independent end-to-end operator tests of whether HiVenues generalizes.

Only after the synthetic campaign is accepted should Fourth Street Bar become the next real-customer gate.

---

# Part VIII — Added journey drift checks

## 16. Mandatory questions

In addition to the 0.1.0 journey checks, ask:

1. Is this workflow authoring the host territory or only the current home page?
2. Does Direction show real structural consequences rather than labels/themes?
3. Can the operator move between route/page surfaces without losing the one-host mental model?
4. Does Preview remain one coherent working context across internal navigation?
5. Are community/social/value capabilities introduced as host actions rather than provider setup tasks?
6. Does mobile use task-appropriate interaction rather than compressed desktop panels?
7. Do icons improve recognition without replacing understandable language?
8. Can the maximal synthetic venue be created entirely through supported Studio workflows?
9. Can that same venue survive Direction/composition changes without semantic loss?
10. Has this journey been proved on synthetic hosts before placing the burden on the first real customer?
